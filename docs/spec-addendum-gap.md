## 追補の位置づけ

つまり、**すでに作った部分のうち追補と食い違うものは、追補に合わせて直す**。

予約台帳と勤怠は、それぞれ単体で 1 プロダクトの規模がある。

いまは POS 本体を仕上げることを優先し、**この 2 つは作らない**。

将来やるときのために、追補 §I.5.2 の指示どおり
`restaurant_tables` と `clerks` に外部 ID の接続点だけは空けておく。

## 4. 進め方（追補 §I.5 の提案に沿う）

追補自身がフェーズ見直し案を持っている（§I.5）。要点:

- **P0 に前倒しすべきもの**: 集計基準・税区分 4 値・`calc_version`・監査ログ基盤・契約ゲート
  → 「後付けが最も高コスト」と明記
- **P2 は POS 端末の実装**（レジ/ハンディ PWA）。ダッシュボードの取引画面は端末が無いと検証できない
- **来店回数・customers は P4 → P2 へ前倒し**（レジのテーブル一覧で新規/リピを出すため）
- **売上予測は P5 → P3**（売上速報の着地見込と一体）
- **予約台帳・勤怠・キオスク・釣銭機は P5（独立スキーマ）**

### 着手順（提案）

1. **P0 の食い違い修正**（上の表 1）— いま直すのが最も安い
2. 注文数量制限・割引/割増・チップ（会計エンジン）
3. CSV 全列定義
4. 緊急事態モード・未送信キュー
5. 決済端末連携

※ 予約台帳・勤怠は対象外。
