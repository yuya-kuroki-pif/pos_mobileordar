# dinii 互換ダッシュボード 実装状況

いただいた開発指示書（`dinii-spec.zip` 同梱の SPEC.md / 60 枚のスクリーンショット）に対する
実装の進み具合を記録する。指示書そのものはリポジトリには含めていない（実データのスクリーン
ショットを含むため）。手元の `SPEC.md` を正として参照すること。

## 最初に整理したこと

指示書 §1.1 に、**ダッシュボードと店舗端末は別プロダクト**と明記されている。

> 店舗側の端末（レジ・ハンディ・キッチンプリンター・キオスク）と顧客向けモバイルオーダー
> （LINE ミニアプリ想定）は別プロダクトだが、本ダッシュボードがそれらの
> マスター設定・集計・分析・CRM 配信 を一手に担う。

これまで作ってきた POS レジ・KDS・モバイルオーダーは**端末側**にあたる。
指示書が対象にしているのは**管理ダッシュボード**で、両者は置き換え関係にない。
そこでリポジトリをモノレポに分けた（§14 の `apps/dashboard/` に倣う）。

```
apps/
  dashboard/   この指示書が対象とする管理ダッシュボード（:3000）
  terminal/    POSレジ / KDS / モバイルオーダー（:3001）
supabase/      両者が共有するスキーマ
```

### 同時に直した既存の不具合

| 症状 | 原因 |
| --- | --- |
| CSV ダウンロードの出力ファイル一覧が空で、何も選べなかった | `'use server'` のファイルから定数を export していた。サーバーアクションのファイルは async 関数しか export できず、クライアントからは `undefined` になる |
| コメント一覧 / アプリ表示確認が 500 になっていた | サーバーコンポーネントから `Typography.Text` のような antd の入れ子コンポーネントを使っていた。クライアント参照の入れ子プロパティは RSC から読めない |
| 卓の QR が開かない URL を指していた | `moUrl` の組み立て（前回修正済み） |

同じ形の間違いを繰り返さないよう、定数は `lib/exportDefs.ts` `lib/reportDefs.ts` のような
ふつうのモジュールに置き、入れ子コンポーネントを使う部分は小さなクライアントコンポーネントに切り出しています。

どちらも **型チェックは通るのに実行時に壊れる** 種類の間違いなので、
画面を足したら必ず一度ブラウザで開いて確かめています
（`docs` 更新時点で、サイドメニューに載っている 84 ルートすべてが 200 で描画されることを確認済み）。

### 画面まわりで直したこと

通しで見ていて気づいた不具合と、使いづらかった点を直しました。

| 直したこと | 何が起きていたか |
| --- | --- |
| 既定ロールに `attract_all` が無かった | **集客セクションのサイドメニューが全ロールで空**だった。画面はあるのに、どのロールでも辿り着けない状態 |
| 既定ロールの `account_audit_logs` が全部 `none` | アカウント操作履歴に誰も入れなかった。法人単位の監査なので法人管理者だけ `view` にした |
| サイドメニューが現在地で光らない | 完全一致で判定していたため、`/menu/123/edit` のような詳細画面では何も選択されていなかった。前方一致でいちばん長く一致したものを選ぶようにした |
| サイドメニューが長くて現在地を見失う | ヘッダーの下に貼り付けて中だけスクロールするようにし、開いている項目まで自動で送るようにした |
| PL 日別 / PL 月別 / 調理配膳時間で月を変えられない | URL の `?month=` は読んでいたのに、画面に月の選択が無かった。`MonthPicker` を足した |
| スコア推移の「前月差」に★が並ぶ | 点差に星評価の書式を当ててしまっていた。増減用の書式（`delta`）を足して、`+2 点` / `±0 点` を色付きで出す |
| いちばん古い月の前月差が `±0` | 比べる先が無いだけなのに「変化なし」に見えていた。`—` にした |
| 調理・配膳時間の数字に単位が無い | `11.4` とだけ出ていた。単位付きの書式（`unit`）を足して `11.4 分` にした |
| PL 日別の曜日が英語 | `1(Tue)` と出ていた。他の画面に合わせて `1(火)` にした |
| PL の売上が「科目未設定」に落ちる | 会計から拾った売上に科目を当てていなかった。売上高（POS売上）の科目へ入れるようにした |
| レシートの支払方法が「その他」 | 支払方法マスターと繋いだ結果、モバイル決済や商品券が enum の `other` に丸められて印字されていた。お客様が選んだマスターの名前を出すようにした（レジの会計一覧も同じ） |
| 編集中にプレビューが流れていく | クーポンとメッセージ配信のスマホプレビューを、スクロールしても付いてくるようにした |

### 指示書に無い追加（Zalo ログイン連携・案A）

ベトナム向け。dinii の LINE ミニアプリに当たる部分を、いまの Web モバイルオーダーのまま実現する。
`/zaloConnect` で業態ごとに設定する。

| Zalo ログイン（OAuth + PKCE） | 🟡 | 実装済み。`ZALO_APP_ID` / `ZALO_APP_SECRET` を入れると動く |
| 顧客の紐付け | ✅ | `customers.zalo_user_id`。顧客は法人単位で 1 人 |
| 来店の記録 | ✅ | `customer_visits` に積み、来店回数・最終来店日を進める |

**設計の考え方**

- 既定は「出す（スキップ可）」。連携必須にすると、その注文自体を失う。
  スキップされても損はしないので、特典を強くするほうが結果的に増える。
  ただし必須にもできるようにしてあり、運用側で選べる。
- 同意は「いつ取ったか」まで残す。ベトナムの個人データ保護（Decree 13/2023）と
  広告メッセージの事前同意（Decree 91/2020）を念頭に置いている。
  実際の運用前に現地の専門家に確認すること。
- app secret とアクセストークンは環境変数に置き、DB にも画面にも持たせない。
- 将来 Zalo Mini App（案B）へ移っても、ここで得る user id の意味は変わらないので、
  顧客まわりのデータはそのまま使える。

**Instagram / Facebook について**

フォローしても相手の情報は取れず、フォロワーへの DM もポリシーで送れないため、
「連携して顧客管理 → 後日お知らせ」の用途には使えない。
フォローボタンを置くだけなら可能だが、顧客の識別と配信は Zalo に寄せている。

## 指示書との差異（意図的なもの）

1. **認証が Supabase Auth ではない。**
   §10.1 は Supabase Auth（招待メール）を前提にしているが、招待メールの導線が未整備のため、
   暫定として `accounts.password_hash`（bcrypt）と HMAC 署名 Cookie で実装した。
   `auth.users` へ移す際は `src/lib/auth.ts` と `verify_account_password` を差し替える。

2. **開店・閉店時刻を `time` ではなく「0:00 からの分」で持つ。**
   §5.12 は閉店 24:00〜 を許容し 31:00（＝翌 7:00）の形で表示するが、
   Postgres の `time` は 24:00:00 までしか持てない。そのため
   `shops.open_time_min` / `close_time_min` と `business_hours` を分単位の整数
   （0〜1860）にし、画面では `HH:MM` の文字列で出し入れする。
   antd の TimePicker も 24 時超を扱えないので、専用の `TimeMinInput` を用意した。

3. **メニューの税率が指示書と二本立てになっている。**
   §5.3 / §8.2 では税率は商品ごとの固定値（10% / 8%）だが、
   これまでに実装した「持ち帰りなら飲食料品だけ 8%」の動的判定も残している
   （`menus.reduced_rate_eligible`）。持ち帰りのある業態では動的判定の方が
   正しいため、`place_order` は
   「持ち帰り かつ reduced_rate_eligible なら店舗の軽減税率、それ以外は `menus.tax_rate`」
   の順で決める。

4. **注文明細の選択肢を jsonb で持っている。**
   §8.5 には `order_item_choices` テーブルがあるが、現状は
   `order_items.options_snapshot`（jsonb）にスナップショットしている。
   伝票・レシート・KDS が動いているため、移行は必要になった時点で行う。

5. **ダッシュボード本体（§5.1）は器のみ。**
   KPI カード 11 種・推移チャート・ランキングは日次集計テーブルが前提のため P3。

6. **レジ操作用パスワードはハッシュだけを保存する。**
   §5.12 の「ドロワーオープン / VOID / テーブルクリア」は `set_shop_password()`
   経由で bcrypt ハッシュのみを書き込み、画面へは「設定済みかどうか」しか返さない。

7. **支払方法等設定を 4 つの URL ではなく 1 画面のタブにした。**
   §5.10 は `/onSitePaymentDetailType` など 4 つの URL に分かれているが、
   ナビゲーション上は「支払方法等設定」の 1 項目なので、`/paymentTypes` の
   タブにまとめた。中身と並びは指示書どおり。

8. **ロゴ・ブランド名・画像素材は流用していない**（指示書冒頭の注意書きに従う）。

9. **自動翻訳に DeepL / Gemini ではなく Anthropic を使う。**
   §5.9 は DeepL / Gemini を挙げているが、AI 店舗診断・目標の一括入力・
   メニューアシスタントですでに Anthropic のキーを 1 本使っている。
   翻訳のためだけに 2 本目の契約を増やしたくないので同じキーに寄せた。
   差し替えるときは `lib/actions/translate.ts` の `askJson` の呼び先だけを変える。

10. **配信の「毎朝 5 時」「毎日繰り返す」はまだ自動で動かない。**
   設定は保存され、画面にも出るが、定時に走らせる仕組み（cron / pg_cron）は未実装。
   いまは画面のボタンを押したときだけ動く。実行基盤を決めてから繋ぐ。

11. **AI が出した数字・文章は、そのまま保存しない。**
   目標の AI 一括入力はフォームに入れるだけ、メニューアシスタントは計画を出すだけで、
   どちらも人が確かめて保存・実行を押すまで反映されない。
   診断コメントも表示のみで、保存はしない。
